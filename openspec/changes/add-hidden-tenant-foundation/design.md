## Context

`kanyue.server` 是 PocketBase 单体，约 50 个业务集合，没有任何租户字段。数据访问一部分集中在 `internal/records`（`Page` 等）和 `internal/coursecredit/store.go`（`list` / `get` / `pageOf` / `create` / `update`），另有约 17 个文件里约 70 处直接调用 `FindRecordsByFilter`、`FindRecordById`、`Save` 等。过滤条件是手工拼接的字符串，这是租户隔离最容易漏掉的地方。

## Goals / Non-Goals

- Goals：
  - 每条业务数据归属一个租户；
  - 所有读写只能在当前租户内发生；
  - 对外行为完全不变；
  - 将来开放多租户时，只需替换租户解析，不用再动每个模块。
- Non-Goals：租户相关的界面、入驻、计费、跨机构身份、插件售卖、老板工作台，见 proposal 的 Non-goals。

## Decisions

### 1. 共享数据库，每行带租户字段
所有租户共用一个 PocketBase 库，每个业务集合有必填的 `tenant` 关系字段。

- 不采用「每个租户一个库」：目标客户是大量小租户，每家一个库会让运维、迁移和备份的成本随租户数线性增长。
- PocketBase 和 SQLite 在第一阶段的数据量下足够用。将来如果单库成为瓶颈，再按租户拆分；因为每行都带 `tenant`，到时可以按它导出。

### 2. 租户范围的 App 是唯一入口
`internal/tenancy` 提供一个租户范围的 `core.App` 包装（`tenancy.Scope(app, tenant)`）。请求进入业务路由时，中间件把 `e.App` 换成它；定时任务用 `tenancy.Job` / `tenancy.Each` 按租户拿到它。业务代码照旧调用 `e.App.FindRecordsByFilter`、`Save` 等，约 70 处调用点、`records.Page` 和 `coursecredit/store.go` 都不用改：

- 读取：`FindRecordsByFilter` / `FindFirstRecordByFilter` 在调用方的过滤条件外面统一包一层 `tenant={:__tenant} && (<filter>)`，调用方的 `||` 不能放宽租户条件；`RecordQuery`、`FindAllRecords`、`CountRecords`、`FindRecordsByIds`、`FindFirstRecordByData` 都附加 `<集合>.tenant = 当前租户`；
- 按 id 读取：其他租户的记录查不到，当作不存在（404），而不是 403，避免泄露其他租户数据是否存在；
- 写入：`Save` 系列由包装填写 `tenant`，覆盖请求体里带来的值；更新或删除其他租户的记录会被拒绝；
- 事务：`RunInTransaction` 里的 `txApp` 也是同一租户范围；
- 只对带 `tenant` 字段的集合生效，平台集合和 PocketBase 系统集合原样透传。

不带租户直接写业务集合会因为 `tenant` 必填而失败，这是兜底。静态检查（`internal/tenancy/guard_test.go`）禁止业务包：执行原始 SQL、自己选择租户、在处理请求时使用 `se.App`，以及不通过 `tenancy.Job` 注册定时任务。迁移、测试数据种子、测试工具、服务装配和网关对接属于平台代码，列入白名单。

### 3. 请求租户解析只有一个替换点
新增一个解析函数，从请求得到租户：

- 第一阶段始终返回默认租户（迁移创建的看乐）；
- 将来可按登录身份所属的租户、小程序码里的机构参数，或网关传来的机构域名来解析。

中间件只作用于业务路由，PocketBase 自己的 `/api/` 和面板 `/_/` 不受租户限制，供平台运维使用。

定时任务（预约过期与履约、课时过期、对账、outbox 投递、续费扫描）改为遍历所有处于启用状态的租户逐个执行，每轮使用该租户范围的 App。课包购买的补偿任务只对开通了支付插件的租户执行。

### 4. 唯一约束改为租户内唯一
- 业务编码和人员标识（手机号、学号、工号、各类 `code`）的唯一索引改为 `(tenant, …)` 组合唯一。
- 幂等键、订单号、操作流水号、支付渠道事件号属于全局技术标识，仍然全局唯一。
- `teachers` 是 auth 集合，其 `username`、`tokenKey` 等认证字段仍按 PocketBase 的要求全局唯一。

### 5. 平台级与租户级的边界
- 平台级、不带 `tenant` 的集合：`tenants` 本身、PocketBase 的 superusers 与系统集合、网关对接（`gatewaylink`）相关配置。
- 其余业务集合（包括 `wechat_identities`、审计日志、outbox）都带 `tenant`。
- 审计日志带租户，平台超管查看时不受限制。

### 6. 核心与插件的边界
- **核心**：所有租户都有的能力，包括机构、成员、课程、课时（权益）及其流水、可约时段、预约、核销、积分和活动。
- **插件**：租户额外开通的能力。第一阶段只有支付插件，范围是课包购买与价格版本、订单、退款、对账、`commerce_*`，以及和 `kanyue.pay` 的对接。`conversion_*`（课时换算）属于核心的权益规则。
- **数据**：插件的数据同样带 `tenant`、同样走收口层，规则不变：业务数据都有租户。
- **开通检查**：`tenant_plugins` 记录哪个租户开通了哪个插件。模块在 `main.go` 里声明 `Plugin`（支付模块是 `payment`），服务装配时记下它注册的路由；请求命中这些路由而当前租户没开通时返回 404，和「接口不存在」无法区分。插件模块自己不重复写这层判断。
- **两级开关**：进程级开关 `COURSE_COMMERCE_ENABLED` 表示这个部署是否提供支付插件，`tenant_plugins` 表示某个租户能否使用；两者都满足时接口才可用。
- **边界方向**：插件可以调用核心，比如支付到账后发放课时；核心不依赖插件。没开通任何插件的租户，核心功能完整可用。
- **将来扩展**：计费、到期、试用都加在 `tenant_plugins` 上，营销优惠插件按同样方式接入。

## Risks / Trade-offs

- **漏改某处查询导致跨租户读写**：
  - 用静态检查禁止新增绕过收口层的直接查询；
  - 用双租户隔离测试覆盖每个模块的列表、详情、写入和定时任务；
  - 现有契约测试原样通过，证明单租户下的行为不变。
- **迁移重建唯一索引时失败**：已有数据都属于看乐，组合唯一不会比原来更严格，理论上不会冲突。迁移仍然先在生产数据备份的副本上演练。
- **工作量**：主要在约 70 处直接查询的迁移和隔离测试；接口、前端和网关不动。
- **插件边界划得太早**：第一阶段只按现有模块划出支付插件，不抽象插件框架。开通检查只是一张表加一个路由包装，以后要调整成本很低。

## Migration Plan

1. 备份 `pb_data`，在副本上执行 `kanyue_0007_tenants`。迁移依次：创建看乐租户并开通支付插件、给各业务集合加 `tenant` 字段并回填、重建组合唯一索引。
2. 在副本上运行契约测试和小程序 live 回归，再在生产执行。
3. 回滚：按项目惯例 `migrate` 只有 up，回滚就是恢复执行前的 `pb_data` 备份。迁移不改写已有业务字段，只新增字段、回填和重建索引，所以恢复备份即可回到原状；回滚后要用旧版本二进制启动。

## Roadmap (later changes, not in scope)

1. **核心约课核销与老板工作台**：
   - 小程序老板工作台：会员列表、发放和调整课时（只追加流水，记录操作人和原因）、到课核销、可约时段；
   - 没开通支付插件的租户，课包页只展示介绍并引导「联系老板」；开通了的租户（看乐）照常在线购买；
   - 小程序通过一个「当前机构已开通的插件」接口决定显示哪些入口。
2. **跨机构身份**：
   - 平台用户（微信或手机号）与「机构成员」分离；
   - 一个人可以在多个机构分别担任学员、老师或老板；
   - 「我的」页的会员卡组展示真实的多张卡。
3. **开放多租户**：机构入驻与开通、按 `joinMethods` 实现的扫码加入与审批、按 `studio` / `individual` / `coach` 分档的套餐、个人和私教档的界面简化（只有一位老师时不显示选老师，没有场地时不显示选场馆）。
4. **课程和商品介绍**：富媒体上传，并接入内容安全检测。
5. **营销优惠插件**：优惠券、体验课、老带新等，作为额外购买的插件；优惠计算在服务端完成，与权益流水关联。
6. **插件售卖**：开通、试用、计费、到期，记录在 `tenant_plugins` 上。

### 7. 学员加入方式由老板多选
加入方式是租户的设置，由老板自己选择，可以多选：有的老板为了尽快拉到足够的学员，希望扫码即成为会员；有的更看重私密，只允许老师或老板主动添加。`tenants.joinMethods` 是多选字段，取值：

- `scan_join`：扫机构码即成为会员；
- `scan_approval`：扫码申请，老板或老师确认后成为会员；
- `staff_invite`：老师或老板主动添加。

第一阶段只存储，看乐默认为 `staff_invite`（与现在的做法一致），没有任何行为读取它；扫码入口和审批流程在开放多租户时实现。
