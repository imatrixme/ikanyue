## Context

现有课程系统已经具备精确课程课时批次、FEFO 预留、课堂名单、教师分配、出勤、核销、冲正和 Outbox。学生小程序通过 `/v1/student/learning/*` 只看到课程、剩余课时、日程和记录；Admin 通过 `/ops/*` 管理课程、课包、班级和课堂。缺口是学员不能利用剩余课时主动提出一对一课程预约，教师也没有小程序工作台维护可预约时间或确认申请。

PocketBase 继续只承担集合、索引和 SDK Batch 事务存储；Hono 持有全部预约、资格、冲突、课时与权限逻辑。开发期间不持续运行 Docker，最终发布门禁才进行真实 PocketBase 并发和恢复演练。当前小程序微信登录只绑定学生，教师小程序身份必须作为本次安全基础补齐。

## Goals / Non-Goals

**Goals:**

- 支持一对一课程的学员申请、教师确认、取消、改期、完成和历史查询。
- 使用数据库唯一约束保证教师、学员和未来可选教室不会被并发重复占用。
- 教师确认时一次性创建正式课堂、预留精确课程课时、建立日历占位并写审计与通知。
- 复用现有课堂出勤、核销、教师工作量和冲正流程。
- 在同一小程序中提供安全的学生/教师角色切换和角色化导航。
- 为 Admin 提供按业务场景组织的预约队列、日历、规则和异常处理工作区。
- 三个受影响项目独立保持四项覆盖率 95% 以上。

**Non-Goals:**

- 不开放小程序报课、支付、课时兑换、二维码签到或自动核销。
- 不开放班课或多人拼课的自助预约；首期预约容量固定为一名学员。
- 不新增独立数据库或 PocketBase hooks。
- 不在官网、Flutter 或旧 Nuxt 项目增加预约入口。
- 不把待确认申请当作教师时间占位，也不提前冻结学员课时。

## Decisions

### 1. 预约确认物化为现有课堂

`appointment_requests` 负责表达申请与确认状态，确认成功后创建 `originType=appointment` 的 `sessions`、一条 `session_students` 和一条主讲 `session_teachers`。后续课时预留、出勤和核销继续使用现有领域服务。创建另一套预约课时流水会导致结算与教师工作量重复，予以拒绝。

### 2. 使用离散时间占位解决并发重叠

时间按 15 分钟原子格写入 `schedule_claims`，开始时间默认按 30 分钟步长展示。每条 active claim 使用 `(ownerType, ownerId, cellStartAt)` 部分唯一索引。确认、Admin 发布课堂、改期和取消都必须维护同一套 claims。仅做“先查后写”的时间重叠检查无法阻止两个并发确认同时成功，予以拒绝。

教师确认会同时声明教师和学员时间；未来结构化教室启用后可复用 `ownerType=room`。一节 60 分钟课程产生四个教师 claim 和四个学员 claim，数量在当前规模下可控。

### 3. 可预约时间由策略、教师规则、例外和占位共同计算

默认策略时区为 `Asia/Shanghai`，窗口为 `[09:00,11:00)` 与 `[14:00,19:00)`。最终可用时间为机构窗口与教师每周规则的交集，加上机构窗口内的临时开放，再减去临时关闭、最早预约限制、已存在 claims 和学员课时有效期限制。教师规则缺失时使用默认窗口；教师不能自行开放机构窗口外时间，Admin 可以显式覆盖。

默认策略为：最早提前 12 小时、最远 30 天、教师响应最长 24 小时且不得晚于开课前 6 小时、学员确认后自助取消截止开课前 12 小时。所有参数存储为版本化 `booking_policies`，预约保存策略快照。

### 4. 申请不占教师时间，确认才进行最终裁决

学员提交申请时检查当前精确课程剩余课时、目标时间有效期、教师资格、开放时间和当前 claim，但不冻结课时、不创建 claim。每名学员同一课程最多保留一个 pending 申请，避免无限占用教师注意力。同一教师时段允许存在多个待确认申请；第一个确认成功者获得唯一 claims，其他重叠申请被标记 `slot_taken`。

确认时重新执行全部资格检查。若课时已被其他课堂预留，申请转为 `eligibility_lost`，教师和学员收到稳定业务提示。

### 5. 确认命令使用一个 PocketBase SDK Batch

确认命令读取带 version 的申请、策略、课程、教师资格、课时批次和当前日历，复用纯规划函数生成：session、session student/teacher、课时 batch movement、allocation、不可变 credit events、schedule claims、appointment event、状态更新和 Outbox。所有写入只调用一次 `createBatch().send()`；任一唯一索引或版本冲突导致全量回滚。

现有 `reservationService` 的发送步骤需要拆成可组合 plan builder 与独立 command wrapper，不能在预约确认中顺序调用两个事务。

### 6. 取消与改期保持课时和时间占位原子一致

pending 申请可由学员撤回。confirmed 预约在自助取消截止前可由学员取消，教师或 Admin 可因教师原因取消；取消在一个 Batch 中释放 active claims、释放课时 allocation、取消 session、更新 appointment 并写事件和通知。截止时间内的学员取消不开放自助操作，由 Admin 按现有课堂规则处理。

教师或 Admin 改期必须先验证新时间，在同一 Batch 中创建新 claims、释放旧 claims、重新校验课时有效期并更新 session 与 appointment；新时间冲突时旧预约保持不变。

### 7. 微信身份与业务角色分离

新增 `wechat_identities` 记录 appId/openId/unionId 与 `student|teacher` principal 的绑定。教师必须已经存在、verified 且未 blocked，微信登录绝不自动创建教师。同一手机号同时匹配学生和教师时返回短期角色选择 challenge；完成选择后签发对应角色 token。“我的”页面允许已绑定身份之间切换。

教师小程序 API 使用 `/v1/teacher/*` 和本人所有权校验，不复用 `/ops/*`。Admin capability 继续用于全局预约管理，并在认证时从持久化教师配置投影，不能只依赖测试构造的 claims。

### 8. 同一小程序使用角色化自定义 TabBar

学生保留“活动、课程、积分、我的”；教师显示“活动、工作台、预约、我的”。课程、日程和预约详情使用角色安全投影，前端隐藏不作为授权。业务图标继续使用 imagegen 资产，微信包内使用小尺寸索引 PNG，空视图资产保持不变。

### 9. 预约过期和通知复用外部调度与 Outbox

外部调度器调用受保护的 Hono worker 将超过响应期限的 pending 申请标记 expired，并投递申请、确认、拒绝、取消、改期和临近上课通知。PocketBase 不运行 cron 或 hook。

## Risks / Trade-offs

- [现有未来课堂可能已经时间重叠] -> 回填 claims 前生成冲突报告，未解决记录进入 Admin 异常队列，启用预约前必须归零。
- [离散 claims 增加记录量] -> 只物化已占用时间，不预生成所有空闲槽；按开始时间和 owner 建索引并定期保留历史归档策略。
- [待确认申请可能竞争同一时段] -> 教师界面明确显示竞争申请数量，确认命令由唯一索引最终裁决并自动关闭冲突申请。
- [确认时课时资格发生变化] -> 申请阶段只作提示性校验，确认阶段强制重新校验并返回 `eligibility_lost`。
- [角色化 TabBar 影响现有学生视觉] -> 复用现有 token、间距和 imagegen 图标，增加编译契约与微信开发者工具截图比较。
- [真实 PocketBase 并发只在最终门禁验证] -> 开发阶段使用纯函数、事务计划和唯一索引契约测试；发布前运行两请求竞争同一 slot 的真实集成测试。

## Migration Plan

1. 先发布新集合、索引和身份字段，保持 booking policy 与 offerings 全部 disabled。
2. 修复教师 capability 投影和微信教师绑定，不改变现有学生登录默认行为。
3. 接入所有未来 session 的 teacher/student claim 写入并运行只读冲突扫描。
4. 回填无冲突的未来课堂 claims，人工处理冲突记录。
5. 发布学员/教师查询和预约命令，Admin 先行管理策略与教师 offering。
6. 以教师和课程为单位启用 offering，先在内部账号验证完整闭环。
7. 最终发布前运行 Docker 迁移恢复、真实 PocketBase 并发、三端覆盖率和微信开发者工具验证。

回滚时禁用所有 offerings 和 active policy，保留已确认 session、claims、课时流水和审计事实；前端隐藏新入口，不删除已产生记录。

## Open Questions

- 教室仍为自由文本，本期只阻止教师和学员时间冲突；结构化教室与 room claim 留待后续。
- 迟取消是否消费课时继续由现有课堂规则与 Admin 处理，本期不在学员端自动执行惩罚性核销。
