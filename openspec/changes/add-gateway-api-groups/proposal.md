## Why

`kanyue.gateway` 一期用“站点 + 路由 + 全量发布”替代了阿里云网关的转发，但运维模型和阿里云不一样，主要有四处：

- 没有 API 分组和 API 这两个对象：接口不能归集到组，组上不能绑定域名，也不能对单个接口配置或上线。
- 配置不分环境：一次发布对 TEST、PRE、RELEASE 同时生效，环境只用来挑后端实例。
- 发布只能全量：登记或修改任何东西，都要和其他所有草稿一起上线。
- 策略只能逐个插件挂载，没有可复用的策略组，也不能锁定“下级不准放宽”的规则；审计只记改后的值。

这些问题要在 `mapi.ikanyue.com` 切流（`add-kanyue-gateway` 任务 5.4、5.5）之前解决，避免切流后再迁移一次配置。

## What Changes

- **API 分组与 API**：
  - 分组绑定域名，每个域名有默认环境，也可以固定为某个环境；
  - API 引用一个已发现的接口，带可见性（公开 / 私有）、鉴权方式（透传 / 应用签名 / JWT / 无）、超时和匹配优先级；
  - 一个分组可以混合多个服务的 API；
  - 对外路径与后端路径一致，需要改写时用 `request-rewrite`。
- **三环境上线（按 API × 环境）**：
  - 登记和修改只改草稿；点击“上线到某环境”才生效，其他环境与其他 API 保持旧配置；
  - 每次上线记录保存解析后的完整定义（含有效策略），可以按 API 回滚、按环境下线；
  - 组设置（域名、默认策略组）作为单独一项按环境上线；
  - 上线 RELEASE 时，与 PRE 当前定义不一致只提示差异、要求填原因，不强制拦截。
- **策略组**：
  - 策略组是可复用的一组策略项（插件 + 配置 + 生效环境 + 是否锁定）；
  - 策略按固定的四层叠加：平台基线 → 分组默认策略组 → API 策略组 → API 覆盖项，应用级在最后；
  - 每层最多一个来源；策略组不能嵌套，也不能多个组合；
  - 锁定的策略项，下层不能修改或停用；叠加型策略（限流）下层只能再加。
- **按环境的快照**：数据面每个环境一份编译好的路由表；上线只重新编译并原子替换受影响的环境。
- **审计**：所有写操作记录改前、改后和差异；上线记录写明环境、涉及的 API 及版本、是否强制和原因；审计只能追加。
- **迁移**：
  - 站点、路由、插件绑定、暴露清单转换为分组、API、策略；
  - 迁移后三个环境都等于当前已发布版本，转发行为不变；
  - 迁移前自动备份。
- **BREAKING（仅网关管理面）**：
  - 全量发布接口 `/gateway/v1/publish`、`/gateway/v1/rollback` 由按环境的上线、下线、回滚接口取代；
  - `sites`、`routes` 集合退役（迁移后只读保留）；
  - 控制台的“站点 / 路由 / 插件 / 发布”页由“API 分组 / API / 策略组 / 上线记录”取代。
  - 数据面对小程序、官网的行为不变。

## Impact

- 规范：
  - 新增 `api-groups`、`api-environment-release`、`api-policy-sets`；
  - 修改 `api-gateway-policies`、`api-gateway-runtime`、`service-api-discovery` 的相关要求。
  - 这些能力定义在尚未归档的 `add-kanyue-gateway` 中，应先归档它，再归档本变更。
- 代码：
  - `kanyue.gateway/internal/{schema,snapshot,control,proxy,exposure}`；
  - 控制台 `kanyue.gateway/console`；
  - `scripts/gateway-exposure.test.mjs`、kanyue.server 清单测试读取的暴露清单格式。
- 数据：网关配置库迁移（新集合、旧集合只读），迁移前备份。
- 文档：`kanyue.gateway/README.md`、部署 skill 与 runbook、`GEB.MD` §8。

## Non-goals

- 不做变更集（跨 API 打包的发布单元）、审批流、多人权限分级。
- 不做对外路径与后端路径不同的参数映射（用 `request-rewrite`）。
- 不改小程序、官网、后台与业务服务的接口和契约。
