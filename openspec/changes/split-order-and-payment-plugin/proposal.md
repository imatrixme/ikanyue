## Why

隐藏租户一期把「支付」登记成了第一个插件，但代码上它还和核心混在一起：`coursecredit` 包里的 `commerce_*` 既管商品订单，又管收款。`commerce_orders` 一张表里同时装着「买了什么、退款规则、退了多少」和「支付单号、付款人、网关状态」。核心的预约取消流程还会直接读写 `commerce_orders` 和 `commerce_refunds`，这是核心反过来依赖插件。

插件按时间收费、会过期。商品订单和支付分不开，过期时就会出现两种问题：要么关了插件，学员连已付订单的退款都办不了；要么插件关不干净。

## Product decisions (confirmed 2026-10-29)

1. **支付流水和商品订单是两个概念**：
   - **订单中心（核心）** 负责与货品订单有关的一切：可售条目、下单、买了什么、价格与分摊、履约（发放课时）、退款和取消规则、退多少、哪些课时要收回、退款单、订单查询；线下和线上订单都用它；
   - **支付（插件）** 只负责与钱有关的事：支付流水（发起支付、查询支付结果、支付回调）、退款流水（执行退款、查询退款结果、重试）、资金对账、资金异常与补偿。它只认识「一笔要收或要退的钱，对应哪个业务单号」，不认识课包、课时和学员的购买内容。
2. **插件只能调用核心，不能反过来**：核心需要回头调用插件的能力（比如营销优惠要介入发放和下单）不做成插件，要么进核心，要么不做。
3. **插件按时间收费，会过期**：插件有「启用 / 收尾 / 停用」三种状态。收尾期不能发起新的支付，但查询、退款、回调、补偿和对账照常进行；已经发放的课时和订单永远属于核心。
4. **平台总开关与网关策略组（2026-10-29 追加）**：
   - 平台可以一键暂停所有租户「发起支付」（渠道故障、风控时用），已在途的钱照常收尾；
   - 网关上把收银台与支付查询单独成批，挂策略组 `payment`，可单独限流或停用。一个域名只能绑定一个 API 分组，所以没有拆成独立分组。

## What Changes

- **订单中心（核心 `coursecredit`）**：
  - `commerce_offers` 改名为 `offers`；
  - 核心 `orders` 增加退款与取消规则、每行实付分摊、已退金额、待退金额、取消扣费，以及结算方式（`offline` / `online`）；
  - 新增 `order_refunds`（退款单）：哪笔订单、整单退还是单节取消、应退金额、扣费、暂扣的课时、状态（待退款 / 退款中 / 已退款 / 已撤销）、结算方式；
  - 下单、订单查询、退款报价与申请、预约取消的退款计算、履约与重新履约、可售条目管理都在订单中心，只读写核心数据；
  - 导出给支付插件的命令：查询应付金额、登记支付成功并履约、登记支付失败、列出线上退款单、登记退款成功、登记退款失败、重开失败的预约退款、按业务单号批量查询订单摘要，以及学员与运营看到的订单 / 退款视图（插件路由原样返回，响应格式不变）。
- **支付插件 `internal/plugins/payment`**：
  - 数据：`payment_transactions`（支付流水）、`refund_transactions`（退款流水）、`payment_cases`（由 `commerce_cases` 改名）、新建的 `payment_claims` / `payment_audit`；原 `commerce_claims` / `commerce_audit` 改名为订单中心的 `order_claims` / `order_audit`，其中「补偿请求」「异常复核」两类审计迁到 `payment_audit`；
  - 支付流水在打开收银台（或 mock 支付）时才创建，下单本身不碰支付；
  - 能力：收银台（按订单中心给的应付金额发起支付）、查询支付结果、支付与退款回调、执行待退的退款单、重试退款、补偿任务、资金总览、对账单、资金异常工单、和 `kanyue.pay` 的对接；
  - 静态检查：核心包不能引用 `internal/plugins/...`；插件不能直接读写核心集合，只能用订单中心导出的命令。
- **插件生命周期**：
  - `tenant_plugins` 增加 `expiresAt`，状态改为 `active` / `winding_down` / `disabled`；到期后自动按收尾处理；
  - 路由声明它需要的插件能力：需要「发起支付」的路由（下单、收银台）只在启用期可用；只需要「资金收尾」的路由（查询支付结果、回调、退款执行、补偿、对账、工单）在收尾期也可用；
  - 停用时，待线上退款的退款单转为线下结算，由老板线下处理；订单与课时不受影响；
  - 新增 `platform_plugins`（按插件一行，`paused`）：平台暂停时所有租户都不能发起支付，收尾能力不受影响。
- **网关**：`mapi.json` 中收银台与支付查询单独一批，挂策略组 `payment`；应用清单前须先在控制台建好该策略组。
- **对外基本不变**：接口路径和响应格式不变，小程序、后台不改。两处可观察的变化：
  - 学员和运营发起的线上退款先返回「退款中」，由支付插件的补偿任务（每 3 秒）或按单同步实际执行，不再在请求里同步调用网关；
  - `POST /ops/commerce/orders/{id}/recover` 归支付插件（同步该单的支付与退款），插件停用后不可用；
  - `commerce-smoke` 改为读新集合（`orders`、`order_refunds`、`payment_transactions`、`refund_transactions`），流程和断言不变。

## Non-goals

- 不做营销优惠，也不为它预留扩展点。
- 不做线下订单登记和「标记已线下退款」的老板界面；这些放到老板工作台阶段。订单中心只保证数据和状态支持线下结算。
- 不改 `kanyue.pay`，不做服务商 / 分账模式；多租户开放支付之前另立变更。
- 不做插件售卖、续费和计费界面；到期时间由平台运维设置。

## Impact

- Affected specs：新增 `order-payment-boundary`。
- Affected code：
  - `kanyue.server`：
    - `internal/coursecredit`：新增订单中心（下单、履约、退款单、取消报价、订单查询、可售条目），预约取消只用订单中心的数据；
    - 新包 `internal/plugins/payment`：原 `commerce_*` 中与钱有关的部分；
    - `internal/tenancy`、`internal/server`：插件三态、平台暂停与按能力开放的路由（路由级中间件 `tenancy.Needs`）；
    - 新迁移 `kanyue_0008_order_payment_split`：扩展 `orders`，新建 `order_refunds`、`payment_transactions`、`refund_transactions`、`payment_claims`、`payment_audit`，改名 `offers`、`order_claims`、`order_audit`、`payment_cases`，转换已有数据；
    - 测试：现有 commerce 测试拆到订单中心和支付插件两侧，补充插件到期与停用的测试。
  - `kanyue.gateway`：暴露清单分批与策略组、对应测试与 README；
  - `scripts/commerce-smoke.mjs`：读新集合；
  - `ikanyue.mini`、`ikanyue.admin`、`kanyue.pay`：不改。
- Data：
  - 看乐还没有开放购买，生产上的订单数据预计为空或只有测试数据；迁移仍然要能转换已有数据，并先在生产备份副本上演练；
  - 回滚就是恢复执行前的 `pb_data` 备份。
