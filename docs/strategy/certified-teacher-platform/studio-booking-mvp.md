## 2. 从松果到看乐：概念映射

| 松果约课 | 看乐体验版 | 说明 |
|---|---|---|
| 场馆（租户） | **场馆**（看乐自有的校区 / 工作室） | 松果中场馆是独立租户；看乐的多个场馆同属一个机构，只是“上课地点” |
| 会员 | **会员** = 持有有效课时的学员 | 松果靠“场馆添加”成为会员；看乐靠“报课”成为会员 |
| 会员卡（次卡＋有效期） | **课时包 / 课程点批次** | 现有课程点系统已支持数量、有效期、按课程类型区分 |
| 常规课（团课） | **班课** | 音乐班课多为固定名单，未必开放自助预约（见决策点 Q7） |
| 私教 | **一对一** | 看乐的主课型 |
| 签到 / 旷课 | **出勤结算 / 缺勤** | 现有课堂结算已支持 |
| 收入报表 | **收入报表（按场馆拆分）** | 现有财务报表需要增加场馆维度 |
| 消息通知 | **订阅消息** | 现有 Outbox 已写入事件，但通知投递尚未接通 |

**和松果最大的两点区别**
1. **入口是开放的，权限是收紧的。** 松果只能“场馆先加会员”，新用户进来就是死胡同。看乐允许任何人登录，但没有有效课时就不能约课，界面要把人自然引到“报课”。
2. **场馆是地点，不是账户。** 学员只有一个账号、一份课时资产，在不同场馆之间切换的只是“去哪里上课”。

## 3. 用户状态与入口

```text
访客（未登录）
  └─ 授权手机号 ─▶ 已登录·未报课
                    ├─ 线上报课并支付 ─────┐
                    └─ 前台线下报课登记 ───┴─▶ 会员（有有效课时）
                                                 ├─ 约课 / 上课 / 消耗课时
                                                 └─ 课时用完或过期 ─▶ 待续费 ─▶ 续费后回到会员
```

| 状态 | 首页显示 | “约课”入口行为 |
|---|---|---|
| 访客 | 场馆信息、课程介绍、“登录” | 引导登录 |
| 已登录·未报课 | 场馆信息、课程与课时包、“去报课”、“预约咨询 / 体验”（见 Q5） | 显示“报课后即可约课”，按钮跳转报课页 |
| 会员 | 课时资产卡、下一节课、快捷约课 | 正常进入约课流程 |
| 待续费 | 课时资产卡显示“已用完 / 已过期”，“续费”按钮 | 提示续费，可查看历史记录 |

**登录顺序**：先授权手机号，再补充资料。手机号已在后台建档的学员（前台线下报课时录入），登录后自动关联，直接成为会员。现有 `POST /v1/user/wechat-login` 已经是“先按微信标识、再按手机号匹配，找不到就新建”的逻辑，可以直接沿用。

## 4. 多场馆逻辑

### 4.1 规则

1. **课时全场馆通用**（推荐，见 Q1）：课时包不绑定场馆，在哪个场馆上课都扣同一份课时。
2. **老师按场馆排班**：老师的每周可约时间要写明在哪个场馆，例如“周一下午在 A 馆，周三全天在 B 馆”。
3. **同一位老师不能同时出现在两个场馆**：现有排期占用机制（`schedule_claims`）已按老师防止时间冲突，跨场馆同样生效。需要时可以在两个场馆之间加通勤缓冲时间。
4. **琴房占用**（见 Q3）：如果某个场馆的琴房数量有限，同一时段可接的课就有上限。现有排期占用机制已支持“占用方类型”，可以把琴房作为一种占用方。

### 4.2 学员端的场馆选择

- 首页顶部显示**当前场馆**，点击可以切换。
- 默认场馆的选择顺序：上次选择的场馆 → 最近一次上课的场馆 → 用户授权定位后最近的场馆 → 第一个场馆。
- “约课”默认在当前场馆内找老师和时段，也可以切换成“所有场馆”。
- “我的约课”跨场馆显示，每条记录都标明场馆，并提供导航。

## 5. 会员端页面清单

底部 Tab：**首页 / 约课 / 我的**（与松果一致，比现有的“活动 / 课程 / 积分 / 我的”更聚焦约课）。积分、活动是否保留在体验版里，见 Q8。

| 页面 | 主要内容 | 状态与边界 |
|---|---|---|
| 登录 | 授权手机号 → 补充姓名、头像（已有资料则跳过） | 授权失败时可重试，也可改用其他方式联系前台 |
| 首页 | 当前场馆卡片（封面、名称、营业时间、地址、电话、导航）；状态卡（未报课时引导报课，会员显示课时与下一节课）；快捷入口；我的近期约课 | 四种用户状态各有一版（第 3 节） |
| 场馆列表 / 详情 | 全部场馆、距离、营业时间、环境图、电话、地图导航 | 未授权定位时不显示距离 |
| 报课 | 课程类型 → 课时包列表 → 详情（价格、节数、有效期、退款规则） → 下单支付 | 线上支付未开通时显示“到店报课 / 联系顾问”（见 Q4） |
| 约课 | 选课程（只列出持有有效课时的课程） → 选老师 → 选日期与时段（标明场馆） → 确认页（扣哪份课时、取消规则） → 结果页 | 没有可用课时、时段被占、超出预约窗口时，分别给出明确提示 |
| 我的约课 | 分页签：待确认 / 已确认 / 已完成 / 已取消；详情页可取消、可导航 | 超过取消截止时间后，取消按钮置灰并说明原因 |
| 我的 | 上课统计（累计、本月、缺勤）；课时资产卡（每种课程一张，显示剩余节数与到期日）；我的订单、课时记录、个人资料、会员协议 | 课时快过期时高亮提醒 |

现有小程序已有对应页面：选课与订单（`courseShop`）、课程订单（`courseOrder`）、预约课程（`appointmentBooking`）、选择预约时间（`appointmentSlots`）、我的预约（`appointments`）、预约详情（`appointmentDetail`）、课时记录（`courseRecords`）、个人资料（`userinfo`）、协议（`agreement`）。**体验版主要是重组信息架构、加入场馆维度和状态引导，而不是从零开发。**

## 6. 业务规则

| 规则 | 现有系统字段（`booking_policies`） | 体验版建议 |
|---|---|---|
| 最早可提前几天约 | `maxAdvanceDays` | 例如 14 天 |
| 最晚提前多久约 | `minLeadMinutes` | 例如 2 小时 |
| 取消截止 | `cancellationCutoffMinutes` | 例如开课前 24 小时；之后取消照常扣课 |
| 老师确认 | `responseTtlMinutes`、`responseCutoffMinutes`（现有流程是学员申请 → 老师确认） | 见 Q2：松果是即时成功；看乐可以对老师已开放的时段改为即时确认 |
| 时段粒度 | `slotStepMinutes`、`claimGranularityMinutes` | 沿用 |
| 课时冻结 | 预约确认时冻结课时，上课结算时消耗，取消时释放 | 沿用 |
| 缺勤 | 课堂结算规则快照 | 见 Q6：缺勤是否扣课 |
| 同一课程只能有一个待确认申请 | 唯一索引 `(studentId, courseSpecId) WHERE status='pending'` | 沿用 |

## 7. 中后台逆推

### 7.1 Admin 模块

| 模块 | 内容 | 现状 |
|---|---|---|
| 场馆管理 | 名称、地址、经纬度、电话、营业时间、封面与环境图、琴房、状态（启用 / 停用） | **新增** |
| 学员管理 | 手机号建档、资料、常用场馆、课时资产、上课记录、跟进 | 已有；**加常用场馆** |
| 课程与课时包 | 课程规格、课时类型、课时包、价格版本、线上商品 | 已有（`course_specs`、`credit_types`、`packages`、`price_versions`、`commerce_offers`） |
| 线下报课登记 | 前台为学员下单并发放课时 | 后端已有发放接口（`/ops/course-credits/orders/:orderId/grant`）；**需确认 Admin 是否有顺手的操作界面** |
| 老师排班 | 每周可约时间、日期例外、开设课程 | 已有（`teacher_availability_rules`、`teacher_availability_overrides`、`teacher_course_offerings`）；**加场馆维度** |
| 课表日历 | 按场馆、老师、琴房查看课堂 | 已有课堂（`sessions`），但地点只是文本字段 `location`；**改为关联场馆** |
| 预约管理 | 待确认、代约、代取消、改期 | 已有；**加场馆筛选** |
| 出勤结算 | 签到、缺勤、结算、冲正 | 已有 |
| 收入报表 | 收款、退款、课时消耗、按场馆和老师拆分 | 已有财务报表；**加场馆维度** |
| 消息通知 | 预约成功、上课提醒、取消、课时即将到期 | 事件已写入 Outbox，**通知投递未接通**；需接入微信订阅消息 |
| 员工权限 | 前台只看本场馆数据 | 体验版可推迟，先由少数管理员统一操作 |

### 7.2 老师端

现有接口已有老师预约看板、预约列表、日历、课表（`/v1/teacher/booking/dashboard`、`/v1/teacher/calendar`、`/v1/teacher/schedule`）。体验版只需要**在老师端的时段和课表上显示场馆**；如果改为即时确认（Q2），老师端的“确认”操作可以弱化为“查看”。

### 7.3 数据改动（最小集合）

| 改动 | 说明 |
|---|---|
| 新增 `venues` | 场馆：名称、地址、经纬度、电话、营业时间、图片、状态、排序 |
| 新增 `rooms`（可选） | 琴房：所属场馆、名称、可用乐器、状态；只有决定管理琴房时才加（Q3） |
| `teacher_availability_rules` 加 `venueId` | 每段每周可约时间属于一个场馆 |
| `teacher_availability_overrides` 加 `venueId`（可选） | 例外也可以指定场馆 |
| `appointment_requests` 加 `venueId` | 预约发生在哪个场馆；写入后不随场馆资料修改而变化 |
| `sessions`、`classes` 加 `venueId` | 替代现有的文本 `location`，保留旧字段做过渡 |
| `commerce_orders` 加 `venueId`（可选） | 用于按场馆统计报课业绩 |
| `students` 加 `preferredVenueId` | 记住学员的常用场馆 |
| `schedule_claims` 增加琴房占用方 | 只有管理琴房时才需要 |

这些都是新增字段或新增集合，按现有规则需要在发布门禁里先备份、再应用迁移。

## 8. 与现有系统的差距汇总

| 类别 | 内容 |
|---|---|
| 可以直接用 | 微信手机号登录与自动关联；课程点（课时）的购买、发放、冻结、消费、过期；预约策略；老师可约时间；预约申请与取消；课堂结算；线上商品与订单（支付目前是模拟渠道） |
| 需要改造 | 小程序信息架构（Tab、首页状态卡、课时资产卡）；预约、课堂、排班加场馆维度；报表按场馆拆分；预约确认模式（Q2） |
| 需要新增 | 场馆集合与 Admin 场馆管理；学员端场馆切换与导航；订阅消息通知投递；琴房（可选） |
| 外部依赖 | 线上报课需要真实的微信支付商户上线；目前支付网关只接了模拟渠道，商户验收和真机支付都还没做 |

## 9. 需要创始人拍板的问题

| 编号 | 问题 | 建议 |
|---|---|---|
| Q1 | 课时是否全场馆通用？ | 通用。学员只认“我还剩几节课”，不关心是在哪个馆买的 |
| Q2 | 学员约课后是即时成功，还是要老师确认？ | 老师已开放的时段即时成功，体验更接近松果；需要评估对现有预约流程的改动量 |
| Q3 | 是否需要管理琴房？各场馆有几间？ | 如果琴房比老师少，就需要管理，否则可以先不做 |
| Q4 | 新学员怎么报课：线上支付、前台线下登记，还是两者都有？ | 体验版先以前台线下登记为主，线上支付等商户上线后再开 |
| Q5 | 未报课的新用户能否约一节体验课，或至少留下联系方式？ | 建议保留“预约体验 / 咨询”入口，由前台跟进后再报课 |
| Q6 | 缺勤是否扣课？ | 建议扣课，并在约课确认页和会员协议里写清楚 |
| Q7 | 班课是否开放学员自助预约，还是只展示课表？ | 体验版先只做一对一自助预约，班课只展示课表 |
| Q8 | 现有的“活动”“积分”是否保留在体验版里？ | 建议从 Tab 中移出，放进“我的”或首页次要入口 |
| Q9 | 家长是否需要在一个微信里管理多个孩子？ | 少儿学员多时需要；否则体验版先一人一号 |

## 10. 建议的实施顺序

1. **场馆数据与 Admin**：新增场馆，排班、预约、课堂加场馆维度，完成历史数据的场馆归属。
2. **会员端改版**：Tab 与首页重构、四种用户状态、场馆切换、课时资产卡、约课流程标明场馆。
3. **报课路径**：前台线下报课登记的 Admin 操作；线上支付等商户上线后开放。
4. **确认模式与通知**：按 Q2 的结论调整预约确认；接通订阅消息。
5. **报表**：收入、课时消耗、出勤按场馆和老师拆分。

每一步上线前都按现有发布门禁执行：备份、迁移、验收、再启用入口。
