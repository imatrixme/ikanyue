# 松果约课拆解与中后台逆推

## 0. 文档信息

- 状态：调研草案 v0.1
- 日期：2026-10-27（America/Los_Angeles）
- 背景：创始人希望当前阶段先做一个“类似松果约课”的微信小程序体验版
- 证据来源：
  - 用户提供的 5 张会员端截图（版本标注 `C V2.8.2`）
  - 松果约课服务号的官方介绍（用户转述）：“专为瑜伽馆、普拉提馆、舞蹈室等设计开发的一款约课管理系统，含会员管理、会员卡管理、排课约课、收入报表、消息通知等功能。交互设计简约、操作高效、功能全面……【开瑜伽馆，都在用松果约课】”
  - 公开网络（必应、百度、搜狗微信）检索不到该产品或其开发公司“北京小松果未来科技有限公司”的其他资料
- 证据等级：
  - **【证实】** 截图中直接可见，或服务号介绍中明确写出
  - **【推断】** 根据截图线索与同类场馆约课 SaaS 的通用做法推断，需要更多截图或试用馆长端确认

---

## 1. 结论

1. **松果约课是“场馆约课 SaaS”，不是约课平台。**【证实】服务号介绍明确写着“专为瑜伽馆、普拉提馆、舞蹈室等设计开发的约课管理系统”，功能范围是会员管理、会员卡管理、排课约课、收入报表、消息通知。每家场馆用它管理**自己已有的会员**，不帮场馆获客，也不让陌生学员找老师。
2. **入口是“场馆先加会员，会员才能约课”。**【证实】馆长先在后台添加会员（以手机号为准），会员在小程序授权手机号后自动匹配；匹配不到就进入“没有找到关联的场馆”页面，**自己注册的新用户因为没有关联场馆，无法约课**。这是一个封闭的会员体系，代价是没有“新客先体验、再办卡”的入口。
3. **核心对象只有五个：场馆、会员、会员卡、课程（常规课 / 私教）、预约。**【证实 + 推断】上课次数、旷课次数、排名都由“预约 + 签到”推导出来。
4. **对看乐的意义**：这正好是上一轮规划里“阶段 1：老师带存量学生上平台的工具”的形态。封闭会员体系没有冷启动问题，方向一致。
5. **一个重要发现**：现有 `ikanyue.taro3` 小程序已经有选课与订单、预约课程、可预约时间、我的预约、课时记录等页面，覆盖了松果会员端的大部分能力。差别主要在于**松果是多场馆（多租户）的，现有系统是单机构的**。体验版走哪条路，取决于创始人想验证什么（见第 8 节）。

## 3. 逐屏拆解

### 3.1 首页（未登录 / 未绑定状态）

| 区块 | 看到的内容【证实】 | 背后的数据与规则 |
|---|---|---|
| 封面 | 全宽场景图，顶部沉浸式，无导航栏标题 | 场馆可配置封面图 |
| 场馆卡片 | 店标占位、“场馆名称”、营业时间“周一至周日 00:00~24:00”、右箭头进入详情 | 场馆基础信息、营业时间 |
| 地址行 | “场馆地址”＋电话、分享两个图标按钮 | 地址；电话调起拨号；分享转发小程序卡片【推断】 |
| 金刚区 | 场馆信息、购卡续费、去约课、约课统计，四个彩色图标 | 场馆详情页、售卡页、约课页、统计页 |
| 分段列表 | 我的约课（选中，绿色下划线）、常规课、私教 | “常规课”是团课排期，“私教”是一对一【推断】 |
| 空状态 | 云朵插画，无文案、无引导按钮 | — |

**体验问题**
- 未绑定场馆时仍显示“场馆名称 / 店标 / 场馆地址”等模板占位，像没配置好的半成品。
- “去约课”金刚区与底部“约课”Tab 功能重复；“约课统计”在首页和“我的”中各出现一次。
- 空状态没有文案，也没有“去约课”“去登录”这类下一步引导。
- 视觉不统一：首页图标是多色，“我的”页是品牌黄，分段下划线却是绿色。

### 3.2 我的（未登录）

| 区块 | 看到的内容【证实】 | 背后的数据与规则 |
|---|---|---|
| 头部 | 黄色背景、默认头像、“请点击登录”、“下午好”、右上角设置 | 按时段生成的问候语 |
| 统计 | 累计上课(次)、本月上课(次)、本月旷课(次)、本月排名 | 来自签到记录；**有“旷课”概念，说明预约后未签到会被记录**；“排名”是场馆内会员的上课次数排名，用于激励【推断】 |
| 会员卡 | 灰色示例卡：示例XXX工作室、会员卡、0次、有效期至 xxxx.xx.xx；红色提示“您还没有会员卡哦” | **次卡＋有效期**是基本卡型；可能还有期限卡、储值卡【推断】 |
| 菜单 | 约课统计、会员协议、我的订单、我的资料 | 场馆可配置会员协议；有线上订单 |
| 页脚 | 松果约课 logo、`For Wechat MiniProgram C V2.8.2` | “C” 表示会员端，推测另有馆长端 / 教练端（B 端）【推断】 |

**可借鉴**：用卡面直观展示“剩余次数＋有效期”，用户一眼就知道还能上几节、什么时候过期。

### 3.3 登录第 1 步：获取头像、昵称

- 【证实】标题“获取你的昵称、头像”；头像（必填）调起微信头像选择（用微信头像 / 从相册选择 / 拍照）；“姓名”（必填）被预填为微信昵称；确定按钮。
- **问题**：字段名叫“姓名”，填的却是昵称。场馆在后台用真实姓名管理会员，昵称会造成对不上人。
- **顺序问题**：先填资料、后授权手机号。可如果手机号匹配失败，前面填的资料就白填了。更自然的顺序是先授权手机号，匹配成功后再补资料。

### 3.4 登录第 2 步：授权手机号

- 【证实】“欢迎您 成为我们的一员”、头像与昵称、“授权手机号码”按钮；页脚“松果约课提供技术支持 / Beijing Xiaosongguo Future Technology Co.Ltd”。
- 手机号是会员的唯一身份标识，用来匹配场馆档案。
- 注意：微信手机号快速验证能力按现行规则可能按次收费，接入前需核实最新规则。

### 3.5 登录第 3 步：匹配失败

- 【证实】红色感叹号、“没有找到关联的场馆”、显示刚注册的完整手机号、两条原因：
  1. 场馆没有添加您成为会员；
  2. 已添加但手机号不一致，请联系馆长修改。
- 只有一个“重新匹配”按钮。
- **问题**：
  - 完整显示手机号，应当打码（例如 185****9286）。
  - 是死胡同：没有“联系场馆”“换个手机号”“扫场馆码加入”等出路。
  - 对新客户不友好：想先体验、再办卡的人进不来。这正是封闭会员体系的代价。

## 4. 产品逻辑推演

### 4.1 核心模型

```text
场馆（租户）
 ├── 员工：馆长 / 前台 / 教练
 ├── 会员（以手机号唯一）── 会员卡（次卡 / 期限卡 / 储值卡）── 消费记录
 ├── 课程
 │    ├── 常规课：固定课表，多人，有容量上限
 │    └── 私教：教练可约时段，一对一
 ├── 排课 ── 预约 ── 签到 / 旷课 ── 扣次 / 扣费
 └── 订单：线上购卡续费
```

### 4.2 主流程

```text
馆长在后台录入会员（姓名＋手机号）并开卡（线下收款或线上购卡）
→ 会员打开小程序 → 授权手机号 → 匹配到场馆
→ 浏览常规课课表或私教时段 → 预约（校验卡是否适用、次数、有效期、容量）
→ 上课前可取消（受取消截止时间约束）
→ 到店签到（扫码 / 教练代签）→ 扣次
→ 未签到 → 记为旷课（可能扣次或限制预约）
→ 统计：累计、本月上课、旷课、排名
```

### 4.3 推断的业务规则（同类产品的常见配置项，需确认）

| 规则 | 常见配置 |
|---|---|
| 预约开放时间 | 提前 N 天开放预约 |
| 预约截止 | 开课前 N 分钟停止预约 |
| 取消截止 | 开课前 N 小时内不可取消，或取消照样扣次 |
| 满员 | 候补排队，有人取消时自动递补 |
| 最少开课人数 | 不足 N 人自动取消并退回次数 |
| 旷课惩罚 | 扣次；或本周 / 本月旷课超过 N 次后限制预约 |
| 卡适用范围 | 某张卡只能约指定课程 |
| 卡有效期 | 开卡即生效或首次上课生效；支持停卡、延期 |
| 每日 / 每周上限 | 同一张卡每天最多约 N 节 |
| 通知 | 预约成功、上课提醒、课程取消、卡即将到期（微信订阅消息） |

## 5. 中后台逆推

### 5.1 角色与端

| 端 | 使用者 | 职责 |
|---|---|---|
| 会员端小程序（C） | 会员 | 绑定、约课、购卡、查看统计与订单【证实】 |
| 馆长端 / 管理后台（B） | 馆长、前台 | 会员管理、会员卡管理、排课约课、收入报表、消息通知【证实，来自服务号介绍】；签到、订单、员工权限、场馆设置等细节【推断】 |
| 服务号 | 场馆与会员 | 产品宣传入口；很可能也是预约、上课提醒等消息的推送渠道【推断】 |
| 教练端 | 教练 | 我的课表、签到、学员名单【推断】 |
| 平台运营后台 | 松果自己 | 开通场馆、套餐计费、版本发布【推断】 |

### 5.2 场馆后台模块

服务号介绍证实了五大块：会员管理、会员卡管理、排课约课、收入报表、消息通知。下表在此基础上细化，细化部分仍属推断。

| 模块 | 功能 | 对应会员端 |
|---|---|---|
| 场馆设置 | 名称、店标、封面、营业时间、地址、电话、会员协议、约课规则（第 4.3 节） | 首页场馆卡片、场馆信息、会员协议 |
| 员工与权限 | 馆长 / 前台 / 教练账号与权限 | — |
| 会员管理 | 手机号建档、批量导入、修改手机号、标签、备注、跟进 | 手机号匹配、我的资料 |
| 卡种管理 | 次卡 / 期限卡 / 储值卡；价格、次数、有效期、适用课程、是否线上售卖 | 购卡续费、卡面 |
| 售卡与开卡 | 线下收款登记开卡、线上订单、续卡、停卡、延期、转卡、退卡 | 我的订单、卡面 |
| 课程管理 | 常规课模板（名称、时长、容量、适用卡）、私教课程（时长、适用卡） | 常规课、私教 |
| 排课 | 课表（日期、时间、教练、教室、容量）、按周重复排课、私教可约时段 | 约课页 |
| 预约管理 | 查看名单、代约、代取消、候补处理 | 我的约课 |
| 签到核销 | 扫码签到、教练代签、批量签到、自动判定旷课 | 统计中的上课 / 旷课 |
| 数据统计 | 上课人次、旷课率、卡消耗、营收、会员活跃排名、教练课量 | 约课统计、本月排名 |
| 通知 | 订阅消息模板与触发时机 | 消息提醒 |
| 支付 | 微信支付（各场馆自己的商户号，或服务商模式下的子商户） | 购卡续费 |

### 5.3 平台运营后台

- 场馆（租户）开通、试用、到期、续费。
- 小程序形态二选一：
  - **一个公共小程序，多场馆共用**：会员靠手机号自动匹配到场馆。截图中的“没有找到关联的场馆”页面支持这种判断。
  - **每家场馆一个独立小程序**：通过微信第三方平台代开发，品牌更独立，但审核和发布成本高。
- 套餐与功能开关、全局模板、版本发布。

### 5.4 数据模型（最小集合）

| 实体 | 关键字段 |
|---|---|
| `tenant` 场馆 | 名称、店标、封面、营业时间、地址、电话、协议、约课规则（jsonb） |
| `staff` 员工 | tenant、姓名、手机号、角色 |
| `wx_user` 微信用户 | unionid / openid、头像、昵称、手机号 |
| `member` 会员 | tenant、姓名、手机号、wx_user（绑定后写入）、状态；唯一约束 `(tenant, phone)` |
| `card_type` 卡种 | tenant、类型（次卡 / 期限卡 / 储值卡）、价格、次数或天数、有效期规则、适用课程 |
| `member_card` 会员卡 | member、card_type、剩余次数 / 余额、生效与到期时间、状态（正常 / 停卡 / 过期 / 已退） |
| `card_ledger` 卡流水 | member_card、类型（开卡 / 预约冻结 / 消费 / 退回 / 调整）、数量、关联预约、操作人 |
| `course` 课程 | tenant、类型（常规课 / 私教）、名称、时长、容量 |
| `schedule` 课次 | course、教练、教室、开始与结束时间、容量、状态 |
| `coach_slot` 私教时段 | 教练、开始与结束时间、状态 |
| `booking` 预约 | member、schedule 或 coach_slot、member_card、状态（已约 / 已取消 / 已签到 / 旷课 / 候补） |
| `order` 订单 | member、card_type、金额、支付状态、微信交易号 |

## 6. 值得借鉴

1. **封闭会员体系**：只服务已有学员，没有冷启动问题。
2. **卡面化的资产展示**：剩余次数和有效期一目了然。
3. **旷课统计与排名**：用数据督促学员按时上课，契合“常态化学习”的理念。
4. **手机号作为身份锚点**：机构线下录入、学员线上自助绑定，迁移存量学员的成本低。

## 7. 需要避开的坑

1. **未绑定状态显示模板占位**：应当显示“加入场馆”的引导页。
2. **匹配失败是死胡同**：应提供“联系机构”“扫机构码申请加入”“换手机号”等出路，并给手机号打码。对看乐而言，还应考虑保留一个“预约体验课 / 留资咨询”的入口：未关联机构的新用户可以提交意向，由机构跟进后再正式添加为学员，而不是直接拒之门外。
3. **昵称冒充姓名**：真实姓名应由机构录入，或在绑定后单独确认。
4. **入口重复**：金刚区与 Tab、首页与“我的”中的统计入口重复。
5. **视觉不统一**：多色图标、黄色主题、绿色下划线混用。

### 音乐教育和健身场馆的差异（直接照搬会出问题）

| 方面 | 健身 / 瑜伽场馆（松果的主场景） | 看乐（音乐教育） |
|---|---|---|
| 主课型 | 团课为主，私教为辅 | 一对一为主，小组课为辅 |
| 资源冲突 | 教室容量 | 老师时段＋琴房 / 乐器同时占用 |
| 使用人与付款人 | 通常是同一个成年人 | 大量是未成年人：**一个家长微信要管理多个孩子** |
| 卡的含义 | 次卡通用于多种团课 | 课时包按课程类型区分（声乐、钢琴、视唱练耳），单价差异大 |
| 课后 | 打卡即结束 | 需要课堂反馈、作业、阶段进度 |

## 8. 对看乐体验版的路线选项

现有 `ikanyue.taro3` 已有页面：选课与订单（`courseShop`）、课程订单（`courseOrder`）、预约课程（`appointmentBooking`）、可预约时间（`teacherAvailability`）、我的预约（`appointments`）、课时记录（`courseRecords`），后台还有课程点、预约、订单和支付网关。

| 方案 | 做法 | 适合验证 | 成本与风险 |
|---|---|---|---|
| A. 在现有小程序上“松果化”改版 | 不改后端模型，重做会员端的信息架构与视觉：场馆首页、卡面资产、我的约课、统计与排名 | 看乐自有学员的约课体验 | 最快；但仍是单机构，不能给加盟机构用 |
| B. 新建多场馆版 | 按第 5 节新建多租户中后台与会员端 | 让外部老师 / 机构试用 | 最慢；要重做多租户、支付子商户、机构后台 |
| C. 现有系统加“机构”维度 | 在现有数据模型上增加机构（租户）归属，会员按手机号绑定机构 | 先自用，再逐步开放给少量合作机构 | 中等；需要评估现有数据和权限改造量 |

**需要创始人回答的关键问题**：体验版是给谁用的？
- 只给看乐自己的学员用 → 方案 A。
- 要给外部老师或机构试用 → 方案 B 或 C。
